Creator Data Hub & Plan 数据复用

统一 Creator Profile、组织内 CRM 数据与 Plan 项目数据，消除 BD 重复填写，并重新定义 My Library。

文档版本v1.0文档状态待评审
创建日期2026-07-13目标角色BD、KOL Manager、产品、研发、数据团队
核心范围Creator Profile / Organization CRM / My Library / Saved Lists / Plan / Proposal Snapshot
一句话目标同一个事实只维护一次；项目页面引用事实，并只保存项目差异。

1. 背景与问题

当前 Creator 相关数据分散在 My Library、Profile 和 Plan。虽然 Contact 已经可以在 Plan 中调用，但 Influencer Geo 与 Social Profile / Linked Account 仍无法复用，导致 BD 在提案阶段重复填写 Profile 已存在的数据。

本期范围校准：Contact 调用链路已存在，本 PRD 不重做 Contact；优先补齐 Social Profile / Linked Account 与 Influencer Geo 的调用能力，并复用 Contact 的现有模式。
问题本质：不是缺少“复制按钮”，而是相同语义字段在多个业务对象中重复建模，且没有统一 Creator ID、Account ID、字段来源与版本快照。

1.1 当前数据分布

页面当前定位当前承载数据主要问题
My Library加入组织收藏夹的 Creator 列表账号指标、标签、组织内数据入口同时像收藏夹、组织数据库和 CRM，定位混合

1.2 根因

Root cause 01

调用能力不完整

Contact 已建立调用链路，但 Geo 与 Social Account 尚未形成相同的引用机制。

Root cause 02

实体边界不清

Creator 公共档案、组织关系、项目选择被当成同一类数据处理。

Root cause 03

缺少来源与版本

用户不知道字段来自 Profile、组织 CRM 还是当前 Plan，也无法冻结已发送提案。

2. 产品结论

推荐方案：建立三层数据模型。Creator Profile 与 Organization CRM 成为数据源；Plan 通过 ID 引用数据，只保存项目特有字段与显式 Override；Proposal 发送时冻结快照。

4. My Library 重定位

当前冲突：“加入 My Library”既像收藏动作，又被视为进入组织数据库，还承载 Contact、Rate Card、Relationship 等 CRM 数据。一个入口承担三个概念，导致用户无法判断加入后的业务含义。

建议：停止让 My Library 同时承担收藏夹与 CRM。将其拆为 My Creators 与 Saved Lists 两个概念。

4.1 目标信息架构

新模块定位包含对象典型用途
Creator Directory平台 Creator 数据库所有可发现 Creator搜索、筛选、查看 Profile
My Creators组织的 Creator CRM与组织产生业务关系的 Creator维护 Contact、Rate Card、Relationship、Owner、Notes
Saved Lists收藏与分组工具用户主动收藏到一个或多个 List 的 CreatorBeauty shortlist、Indonesia creators、Client A candidates
命名建议：现有 My Library 若短期无法拆分，第一阶段至少更名为 My Creators，并明确其为组织 CRM；后续新增 Saved Lists 承接收藏场景。

5. 核心流程

5.1 Creator 加入 Plan

  1. 1用户从 Directory、My Creators 或 Saved List 选择 Creator。
  2. 2系统创建 plan_creator，保存 creator_id，不复制 Creator 基础字段。
  3. 3若 Creator 只有一个可用 Social Account，默认选中；存在多个账号时要求用户选择。
  4. 4新增能力自动读取 Influencer Geo 与 Social Accounts；Contact 继续沿用当前已有调用逻辑。
  5. 5Geo 或 Social Account 缺失时显示“Complete profile”，补全后自动回填当前 Plan。
  6. 6用户只填写 Manager、Vetting、Deliverables、Proposal Price 等项目字段。

5.2 编辑继承字段

用户在 Plan 点击继承字段时，不直接进入普通输入态，而是先选择修改范围：

编辑 Influencer Geo

Current source · Profile MY

Update Creator Profile影响未来 Draft PlanOverride for this Plan仅当前项目
Plan Override 必须记录 field_name、override_value、source_value、operator、updated_at，并允许一键 Reset to Profile。

5.3 Proposal 生成与锁定

  1. 1点击 Proposal 前执行完整性校验：Linked Account、Geo、Contact、Deliverables、Price。
  2. 2生成 Proposal Version，并保存所有客户可见字段的快照与来源版本。
  3. 3Proposal Sent 后，不因 Profile / CRM 更新而自动变化。
  4. 4若需要采用新数据，创建新版本并显示版本差异。

6. 需求·功能·交互

P1 · Creator Profile

Profile 页面拆分“平台标准档案”和“组织私有数据”，避免用户误认为所有字段都是公共数据。

① 字段

Creator Basics：Name、Primary Geo；Social Accounts：Platform、Handle、Account URL、Metrics；Organization Data：Contact、Relationship、Tags、Rate Card、Notes。

② 规则

Creator Basics 和 Social Accounts 使用全局 Creator / Account ID；Organization Data 按 org_id 隔离。

③ 交互

增加字段来源标签与 Last updated。Linked Account 的新增 / 关联只能在 Profile 完成。

P2 · My Creators

My Creators 是组织 CRM 列表，不再使用“是否收藏”作为唯一进入条件。

8. 分阶段落地方案

阶段范围用户价值依赖
P0 · 数据打通统一 Creator ID / Account ID；Plan Geo 与 Linked Account 改为引用；展示来源直接解决重复填写与账号无法复用数据映射与历史数据迁移
P1 · CRM 定位My Library 更名 My Creators；拆分公共 Profile 与组织数据；自动进入规则明确组织数据归属org_creator 数据模型
P2 · Override & SnapshotPlan Override、Reset、数据更新提示、Proposal Version Snapshot兼顾复用与历史一致性版本服务与审计日志
P3 · Saved Lists多收藏夹、团队协作、批量加入 Plan / Outreach补齐真正的收藏场景列表与权限模型
MVP 建议：优先完成 P0 + My Library 更名。Saved Lists 可以后置，但不要继续在 My Library 上叠加更多 CRM 与收藏混合能力。

11. 待确认项（附推荐默认值）

#问题推荐默认值
1My Library 是否允许直接更名？是，先更名为 My Creators；Saved Lists 后续新增。
2加入 Saved List 是否自动进入 My Creators？否，收藏与 CRM 关系拆分。
3加入 Plan 是否自动进入 My Creators？是，Plan 表示已产生组织业务关系。
4Geo Override 是否允许？允许，必须显式标记且可 Reset。
5Profile 更新是否自动改变 Draft Plan？未 Override 字段自动更新；Review 状态提示确认；Sent Proposal 不变。
6Rate Card 更新后 Proposal Price 是否联动？不自动联动。Rate Card 仅为报价参考，项目价格属于 Plan。
7Contact 是否可以进入客户 Proposal？默认不进入，仅内部协作使用。
